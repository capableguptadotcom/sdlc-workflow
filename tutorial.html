01 · ORIENTATION

A repository contract, not another chatbot.

AI SDLC installs a governed development workflow into an existing Git repository. Your assistant reads that committed contract and follows it. The kit does not install, authenticate, or replace the assistant.

What it gives you

  • A durable root AGENTS.md contract.
  • Thirteen focused skills with three memorable front doors.
  • Progressive specifications, plans, ADRs, and evidence.
  • Repository-specific command mapping in ai-sdlc.yaml.
  • Deterministic validation and behavioral evaluation fixtures.
  • Thin adapters for different assistant surfaces.

What it does not give you

  • A model account, API key, or Codex sign-in.
  • A promise that model output is deterministic.
  • Automatic deployment, monitoring, or production access.
  • Permission to commit, push, publish, or delete.
  • A replacement for tests, CI, code owners, or human judgment.
  • Cross-version kit upgrades in this alpha.

The invariant is “no evidence, no merge”—not “no AI chat, no merge.” Assistants propose and execute bounded work; repositories preserve decisions and deterministic systems decide whether evidence exists.

02 · FIRST ADOPTION

Your first ten minutes.

Start from a real repository with an initial commit. Preview first, apply deliberately, inspect the diff, run both kit and project checks, then commit the contract like ordinary source code.

Preflight

Terminal · repository root
node --version       # v22 or newer
git --version
git status --short  # must be empty before apply
If this is a new project, create the first commit before adoption. That baseline is the installer’s rollback boundary and makes the generated diff reviewable.

Preview, apply, validate

Terminal · public alpha
# Preview: inspect actions, write nothing
npx @innovate-x/ai-sdlc@alpha --dry-run

# Apply without an interactive confirmation prompt
npx @innovate-x/ai-sdlc@alpha --yes

# Validate the installed structure and artifacts
python scripts/validate_ai_kit.py

# Review ownership, project command mapping, and package impact
git diff --stat
git diff

# Run the commands the installer mapped into ai-sdlc.yaml
# Example only—use your repository's actual commands
npm test
npm run lint

# Commit only after review
git add AGENTS.md CLAUDE.md .github .agents .ai specs \
  scripts ai-sdlc.yaml
git commit -m "chore: adopt AI SDLC workflow"

# Same version becomes a read-only integrity check
npx @innovate-x/ai-sdlc@alpha --yes

Adoption checklist

What the installer owns—and what remains yours

Kit-owned files are recorded in .ai/kit.lock.json. Existing shared instruction files receive a clearly marked managed region instead of being replaced. Project-specific configuration, including your edited ai-sdlc.yaml, stays project-owned.

A missing, duplicated, or modified managed region fails safely. A non-managed same-path collision aborts the atomic adoption. The alpha chooses safety over guessing how to merge unrelated content.

04 · THE WORKFLOW

Describe the work normally. Structure appears only when earned.

Developers should not memorize thirteen skills. Three front doors cover the routine journey, while the assistant routes internally according to uncertainty, risk, and lifecycle state.

Build

develop

Orient, shape, plan only when needed, implement bounded slices, and verify.

Complete

finish

Run mapped checks, review the verified diff, surface limitations, then honor the requested Git boundary.

Understand

learn

Pause, teach in context, preserve a redacted handoff, test transfer, and return to the pending decision.

Routing is based on the kind of uncertainty

Your situationExpected routeWhat should not happen
“Explain this repository.”Read-only orientationNo files changed; no ceremonial plan.
“Rename this label and update its test.”Tiny direct changeNo feature specification.
“Add team invitations.”Inspect, then shape unresolved product behaviorNo implementation before rendered spec acceptance.
“I know the outcome but not how.”Agent investigates and recommendsDeveloper is not asked to make routine engineering decisions.
“Polling, SSE, and webhooks all look reasonable.”Focused comparison or simulated perspectivesNo organization-wide initiative map for one choice.
“Will this meet a 200 ms target?”Bounded throwaway prototypeNo production architecture built to answer an experiment.
“Identity, billing, regions, migration, and rollout.”Initiative mapNo opaque one-shot implementation.
“Diagnose this; do not fix it.”Evidence-first diagnosisNo product code edits.

Progressive artifacts

Inline brief

Tiny, local, obvious work. State intent and verification in the conversation.

spec.md + verification.md

Observable behavior, failure rules, and how independent checks will prove it.

plan.md

Only when implementation spans meaningful slices or sequencing matters.

ADR or initiative map

Only for durable trade-offs or several coordinated outcomes.

Draft creation and human acceptance are separate turns. “You answered my questions” is not the same as “you reviewed and accepted the rendered contract.”

05 · REAL WALKTHROUGH

The Pantry Ledger, turn by turn.

The alpha.4 experiment began with a one-route Node server and ended with a persistent inventory application, retry-safe maintenance release, operations runbook, rollback proof, and retirement guidance. Every assistant turn ran inside the isolated environment.

1 · Shape the productNo code
Human: “Turn this starter into a useful Pantry Ledger… I have not worked out all the behavior.”
Assistant: Inspects first, identifies whole-number stock as the highest-leverage product question, and recommends a default.
2 · Render a draft contractDraft only
Human: Settles API, persistence, validation, stock, corrupt-data, and accessibility behavior.
Assistant: Creates draft spec.md and verification.md; changes no product code; asks for explicit acceptance.
3 · Plan the smallest reliable slicesAccepted spec
Human: Explicitly accepts the rendered behavior contract.
Assistant: Drafts three vertical slices: persistence, safe movement behavior, accessible page and docs. Stops again.
4 · Implement and verifyAccepted plan
Human: Accepts the plan and authorizes local implementation, not Git or deployment.
Assistant: Implements, fixes a red test matcher, runs tests/lint/build/audit/whitespace, and performs triggered security and UI reviews.
5 · Create the local releaseOne commit
Human: Accepts behavior and authorizes exactly one local commit.
Assistant: Adds a bounded live smoke test with verified shutdown, reviews the final scope, then creates only the authorized commit.
6 · Diagnose an incidentRead-only
Human: Reports duplicate distribution after a timeout; asks for diagnosis only.
Assistant: Reproduces “applied but response unseen,” proves the API lacks request identity, and leaves the worktree clean.
7 · Teach at the decisionLearn
Human: Pauses to understand idempotency keys.
Assistant: Explains the exact Rice retry, saves a redacted handoff, asks a transfer question, and returns to the pending policy.
8 · Return accepted behavior to draftMaintenance shaping
Human: Defines header, canonicalization, replay, mismatch, persistence, legacy compatibility, and browser retry policy.
Assistant: Updates only the spec and verification contract, then stops for review—again, no product code.
9 · Make the causal fixRed → green
Human: Accepts the revised contract and authorizes one maintenance commit.
Assistant: First proves the gaps with failing tests, then adds durable replay state and browser identity retention, runs bounded live probes, reviews, and commits.
10 · Operate, rollback, retireRunbook
Human: Requests startup, health/log visibility, restart, shutdown, backup, recovery, rollback, and retirement guidance.
Assistant: Corrects a shell-wrapper lifecycle test, verifies process shutdown, documents rollback data caveats, runs all checks, and creates one docs commit.

What the result does—and does not—prove

Supported conclusion

In this controlled project, the repository contract caused the assistant to preserve explicit human acceptance, run stronger lifecycle checks, discover a persistence compatibility defect, and finish operations/rollback work that the baseline could not.

Unsupported conclusion

One stochastic pair does not prove universal productivity gains or statistical causality. Turn counts differ by design because the with-kit arm includes human approval boundaries.

Nine with-kit commands failed deliberately during red tests, negative probes, or corrected attempts. This is healthy evidence: every command had a terminal state, none was interrupted, and the owning turn resolved the failure before its gate passed.
07 · PROMPT COOKBOOK

Useful requests sound like ordinary engineering.

Include intent, important constraints, and authorization boundaries. Do not prescribe internal skill names unless you are testing routing. The assistant should absorb routine technical decisions and return product policy or durable trade-offs to you.

Orientation
“Give me an architecture overview. Explain the request path and where tests prove it. Do not modify files.”

Expected: inspect, explain, cite files, remain read-only.

Tiny change
“Rename the Save button to Save draft and update its existing test. Keep this local; do not commit.”

Expected: direct bounded change, no feature spec.

Fuzzy feature
“Add team invitations. I know the goal but not the behavior. Inspect first, recommend defaults, and stop at human approval boundaries.”

Expected: focused product questions, then a rendered draft.

Unknown approach
“We need offline read access. I do not know how to build it. Investigate the repository and recommend the lightest reliable approach.”

Expected: agent-owned technical investigation; no initiative by reflex.

Diagnosis only
“Checkout sometimes creates two orders after a timeout. Diagnose the cause only. Do not change files.”

Expected: reproduce, isolate, explain evidence, clean worktree.

Test-first fix
“I accept the retry contract. Add a regression that fails for the causal bug, make the smallest fix, run mapped checks, but do not commit.”

Expected: red evidence before implementation, then full verification.

Finish
“Finish this change for human review. Run every relevant mapped check and triggered review. Report limitations. Do not commit.”

Expected: evidence-backed verdict, no authorization expansion.

Learn
“Pause here and teach me why this migration needs dual reads. Save a redacted handoff, ask one transfer question, then return to the decision.”

Expected: contextual teaching without losing workflow state.

Operations
“Exercise startup, health, logs, restart, and clean shutdown locally. Add backup, recovery, rollback, and retirement steps. Do not deploy.”

Expected: bounded lifecycle probe and honest scope limits.

Large initiative
“Introduce multi-region identity, billing failover, data migration, and staged rollout. Map the initiative before proposing implementation.”

Expected: coordinated outcomes and dependencies, not one giant plan.

A strong prompt contract

Reusable shape
Goal:
  What useful outcome should exist?

Known behavior and constraints:
  What is already settled?

Uncertainty:
  What do I need the assistant to investigate or return to me?

Evidence:
  What must pass or be demonstrated?

Authorization:
  May it edit? commit? push? publish? deploy? delete?
08 · BUILDING WITH OPENAI MODELS

The model is a reasoning engine inside a controlled system.

AI SDLC itself is model-agnostic repository guidance. The retained release experiment used Codex CLI 0.145.0 with gpt-5.6-terra as a fixed experimental identity. If you build your own assistant, combine a model with repository context, narrowly authorized tools, structured outputs, and independent evals.

Repository truth
AGENTS.md, specs, ADRs, commands, current diff
→
OpenAI model
instructions, conversation state, tool selection
→
Deterministic boundary
schemas, command events, tests, policy, human gates

1. Put durable behavior in the repository

Keep stable instructions in AGENTS.md, not only in a hidden system prompt. The same reviewed contract can then guide Codex, Claude, Copilot, or a custom assistant. Agent-specific files should be thin adapters, not competing policy copies.

2. Use the Responses API for a custom OpenAI integration

OpenAI recommends the Responses API for new projects. It supports multi-turn state and tool-using agent loops. A minimal reasoning call can keep the repository contract separate from the current developer request:

JavaScript · conceptual assistant seam
import OpenAI from "openai";
import { readFile } from "node:fs/promises";

const openai = new OpenAI();
const contract = await readFile("AGENTS.md", "utf8");

const response = await openai.responses.create({
  model: process.env.OPENAI_MODEL || "gpt-5.6",
  instructions: contract,
  input: [
    {
      role: "user",
      content: "Diagnose the duplicate order after timeout. Do not change files."
    }
  ],
  store: false
});

console.log(response.output_text);
This minimal example generates guidance; it is not yet a coding agent. A real implementation must add repository read/search tools, a bounded command runner, patch application, permission checks, event capture, timeouts, cleanup ownership, and filesystem auditing.

3. Make machine-facing results structured

Human prose can vary; pipeline decisions should not. OpenAI’s Structured Outputs can constrain model responses to JSON Schema. AI SDLC’s behavior harness uses this principle for stable route, mode, verdict, question, artifact, command, and limitation fields—then scores actual filesystem and command events independently.

Example result contract
{
  "mode": "diagnose",
  "verdict": "ready",
  "human_gate": "none",
  "files_changed": [],
  "commands_run": ["npm test"],
  "limitations": [
    "Reproduced with a disconnected local client, not a production proxy."
  ]
}

4. Separate discovery, audit, policy, and authority

Model-owned

  • Inspect relevant repository context.
  • Recommend routine technical choices.
  • Generate candidate implementation and review findings.
  • Explain uncertainty and known limitations.

System- or human-owned

  • Tool permissions, sandbox, budgets, and timeouts.
  • Test, scan, lock, and policy enforcement.
  • Product acceptance and durable trade-offs.
  • Commit, push, publish, deployment, and destructive actions.

5. Evaluate trajectories, not eloquence

OpenAI’s evaluation guidance emphasizes repeatable feedback loops. For coding workflows, score what the assistant did: actual tool calls, files changed, artifact state, Git state, test outcomes, interrupted processes, and whether it crossed an authorization boundary.

Weak measurementStronger measurement
“The answer sounded careful.”Forbidden files unchanged; no unauthorized command event.
Assistant says “tests passed.”Captured terminal event with exit 0 and bounded duration.
JSON says “diagnose.”Filesystem audit confirms no product changes.
Model says “ready.”Independent product oracle, clean checkout, and rollback gate pass.

6. Treat cost as an observable trade-off

The with-kit experiment used more turns and roughly 2.4× the input tokens of the baseline. Spend context on high-risk boundaries, not on ritual. Use smaller or faster models for routing and deterministic preparation only after evals show they preserve behavior; reserve stronger reasoning for complex shaping, diagnosis, migration, or review.

11 · TROUBLESHOOTING

When the safe behavior feels like a blocker.

“The installer says my worktree is dirty.”

Preview is allowed; apply is not. Commit or deliberately stash your project changes, confirm git status --short is empty, then rerun. This prevents adoption files from being mixed with unrelated work and makes rollback intelligible.

“A file already exists at a kit-owned path.”

The alpha aborts atomically instead of guessing. Shared root instruction files have explicit managed-region support; arbitrary same-path files do not. Review the collision and choose ownership manually in a branch.

“The validator warns about empty command lists.”

Confirm whether that role applies. The installer maps recognized Node script names and explicit Python tool configuration; it does not guess ambiguous roles. Fill applicable commands and accept that truly absent roles remain empty. The current warning is accurate but intentionally conservative.

“My repository already uses Husky or pre-commit.”

Existing managers remain the source of truth. Husky composition occurs only for an explicit precommit, pre-commit, or lint:staged script. A Python pre-commit config is preserved. When both managers exist, composition is skipped to avoid duplicate checks.

“I already installed alpha.1. Can I run @alpha?”

Not as an in-place update. Pin npx @innovate-x/ai-sdlc@0.1.0-alpha.1 for its same-version validation, or evaluate alpha.4 in a fresh branch or repository. The CLI rejects a different installed version before writes.

“The assistant used a different route than expected.”

Check actual behavior before checking its label. Did it edit when asked only to diagnose? Did it implement before explicit acceptance? Add a focused dialogue or executable regression for a real failure. Do not leak the expected answer into the model prompt or schema; that makes the evaluation self-fulfilling.

“A test server never stopped.”

Treat this as a failed phase even if the final prose says ready. Own process startup, bound the health probe, register cleanup before assertions, stop in a failure-safe path, and verify both process exit and listener removal.

“Adoption changed what my npm package would publish.”

Inspect npm pack --dry-run --json. Adopted workflow files can dramatically enlarge a default manifest. Use the project’s existing files or ignore policy to make an explicit inclusion decision; a successful pack command alone is not a privacy review.

Install the contract into a clean repository. Describe work normally. Let complexity earn artifacts. Keep product acceptance and external authority human. Measure actions, not claims. Preserve failures. Finish with independent evidence and an operable rollback story.
