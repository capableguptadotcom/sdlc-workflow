01 · Mental model

Five moves, from request to evidence.

The amount of ceremony grows only when uncertainty or risk grows. A button rename stays tiny. A fuzzy product feature earns a behavior contract. A multi-outcome program earns an initiative map.

01

Describe the goal

Use normal language. Include the outcome, problem, or uncertainty.

02

Inspect first

The assistant reads code, tests, decisions, and project guidance.

03

Settle decisions

You choose product policy and durable trade-offs—not routine code details.

04

Build a slice

The assistant implements the smallest useful, reviewable behavior.

05

Finish with proof

Checks, review, and the final diff support the readiness claim.

The developer owns

  • Desired product behavior and business policy
  • Acceptable risk and material trade-offs
  • Acceptance of behavior contracts and consequential plans
  • Authorization to commit, push, publish, deploy, or mutate trackers

The assistant owns

  • Repository inspection and fact finding
  • Routine implementation choices that follow local evidence
  • Focused questions with a recommendation and trade-offs
  • Implementation, deterministic checks, review, and evidence

Creates

Human gate

Evidence

Referenced files and runnable commands.

03 · How special modes trigger

No magic phrase required.

“Grill me,” “simulate a discussion,” and “Wayfinder” are useful labels, but the routing signal is the shape of the uncertainty. Developers describe the problem; the assistant chooses the tool.

MISSING PRODUCT POLICY

Focused grilling

The repository cannot answer who may invite, what expires, or which failure behavior the product should expose. The assistant asks one consequential question at a time, with a recommendation.

shape-change → focused questions
SEVERAL DEFENSIBLE CHOICES

Simulated discussion

Polling, webhooks, and server-sent events all fit. Relevant perspectives compare consequences; the assistant recommends one, while the developer owns the durable choice.

shape-change → compare perspectives
ONE MEASURABLE UNKNOWN

Bounded prototype

The team does not know whether IndexedDB meets a latency target. A throwaway experiment answers that one question and does not quietly become production architecture.

prototype → measure → discard or record
SEVERAL OUTCOME TRACKS

Wayfinder initiative map

Identity, regional data, billing, and multiple channels cannot stay coherent in one feature spec. The assistant maps outcomes and dependencies before each outcome returns for its own spec.

guarded initiative mapping
ROUTINE TECHNICAL CHOICE

Assistant decides

Naming, serializer patterns, and file placement follow existing repository evidence. The assistant should not turn every normal engineering choice into a meeting.

inspect → implement
EXTERNAL OR VERSION-SENSITIVE FACT

Bounded research

When an SDK capability or current standard matters, the assistant verifies primary sources and records only the limitation needed for the decision.

research → cite → return
!

Saying “I have no idea how to implement this” does not automatically trigger a long interview or an initiative map. The assistant first separates missing product behavior from technical uncertainty, then uses repository evidence, research, discussion, or a prototype only where each is actually useful.

00 Adopt the workflow into a repository One maintainer action; no extra clone for the team

A repository maintainer runs the adopter once. It previews the complete installation, preserves supported project-owned guidance, maps recognized Node and Python commands, and asks before writing. 

# After alpha publication
cd /path/to/existing-project
npx @innovate-x/ai-sdlc@alpha

Start from a clean worktree. The adopter will still show a preview on a dirty tree, but it will not apply changes.

Review the preview. Check files, command mappings, hook behavior, and any ownership conflicts.

Confirm once. The write is transactional and validated; a lock records managed ownership.

Review and commit the installed contract. Everyone else receives it through the project’s normal clone or pull.

Ask for a read-only overview. This verifies that the assistant can find and use the installed guidance.

ALPHA

01 Make a clear, tiny change Keep small work small
Developer

Change the settings dialog button from Save to Save changes and update the focused test.

Assistant

This is clear, local, reversible, and low risk. I’ll make the smallest edit and run the focused UI test; no feature folder or planning ceremony is needed.

Inspect the component and its focused test.

Change only the label and assertion.

Run the focused test and inspect the diff.

Report readiness with the exact evidence.

Lightest artifact level

Creates: code, focused test change, verification summary.

Skips: feature folder, specification, plan, ADR, tracker ticket.

Human gate: none until an external action is requested.

02 Start when the approach is unknown The developer knows the outcome, not the implementation
Developer

I want users to access recent records offline, but I have no idea how to implement it.

Assistant

I’ll inspect data loading, caching, authentication, and mutation paths before asking you to make decisions.

Assistant

The product decision is read-only access versus queued writes. I recommend read-only first because queued writes require synchronization and conflict policy. Which behavior do you need?

Separate product uncertainty from technical uncertainty.

Ask only for unresolved product behavior. Bring a recommendation.

Use evidence for the implementation approach. Repository patterns first, primary-source research second, bounded prototype only for a measurable unknown.

Draft the behavior and verification contract. Wait for acceptance before material implementation.

Plan only if multiple slices or material risk warrant it.

What not to do

  • Ask the developer to design caching internals
  • Start an initiative map for one coherent feature
  • Debate what a small experiment can measure
  • Implement before behavior is accepted
03 Diagnose and fix a failure Prove the cause before patching
Developer

Checkout retries sometimes charge the customer twice. Find the cause and fix it.

Assistant

I’m diagnosing before changing product code. I’ll reproduce the behavior and inspect the checkout boundary, tests, history, specs, and relevant decisions.

Reproduce the failure or establish observable evidence.

Trace the causal boundary. Do not patch the first suspicious line.

Add a regression test that can fail for the right reason.

Make the smallest causal fix.

Run focused and affected checks, then review the diff.

Evidence to expect

  • Reproduction or diagnostic evidence
  • Root cause stated clearly
  • Regression red before the fix
  • Focused and affected suites green
  • No broad permanent instrumentation
04 Resolve a contested technical direction Use discussion, research, or a prototype for the right question
Developer

Polling, webhooks, and server-sent events all seem viable. Help me choose.

Assistant

I’ll verify the repository constraints, compare the consequences from the relevant operational, product, and implementation perspectives, then recommend one option. You’ll own the durable choice.

Inspect constraints first. Eliminate options that do not fit.

Classify the remaining uncertainty. Current fact → research. Measurable claim → prototype. Value trade-off → discussion.

Compare consequences, not personalities. Reliability, latency, operations, cost, and migration impact.

Recommend one option and name the downside.

Record an ADR only if the decision is durable, hard to reverse, and surprising without context.

Direct invocation is optional

Developers may say “simulate a discussion” or “grill me,” but ordinary language should trigger the same behavior when the uncertainty fits.

05 Map a large, foggy initiative Wayfinder is guarded, not the default
Developer

Build one customer platform for web, mobile, partner APIs, regional data residency, and usage-based billing.

Assistant

This contains several coordinated outcomes and decision tracks. I recommend an initiative map before feature specs or implementation tickets.

Confirm that several coherent outcomes truly exist.

Map outcomes, decision tracks, dependencies, and unknowns.

Start with the constraining decision. For example, tenant boundaries may constrain regional data and billing.

Return each coherent outcome for its own behavior contract.

Create implementation tickets only after accepted slices and explicit authorization.

Wayfinder should not trigger when

  • The feature is coherent but technically unfamiliar
  • One product decision is unresolved
  • A normal plan has several implementation steps
  • The work can stay in one reviewable behavior contract
06 Finish before committing Authorization is specific; evidence comes first
Developer

Looks good. Commit it.

Assistant

That authorizes the commit, but I’ll finish first: run configured checks, review against intent and repository standards, simplify only when useful, and rerun affected checks.

Run the smallest relevant checks, then configured checks for the affected scope.

Review against the request, accepted behavior, and repository standards.

Apply only authorized blocking fixes or useful behavior-preserving simplification.

Rerun affected deterministic checks and inspect the final diff.

Create the requested commit. Do not push, open a pull request, deploy, or merge without separate authorization.

Ready means

  • Known relevant checks pass
  • The diff matches the accepted intent
  • Limitations are stated
  • No unauthorized external action occurred
  • The working state is reported clearly
05 · Progressive artifacts

Artifacts are earned by complexity.

These levels are not a checklist. Use the lowest level that keeps behavior, risk, implementation order, and durable decisions clear.

LEVEL 0

Inline brief

Clear, local, reversible, low-risk work.

LEVEL 1

Behavior contract

spec.md + verification.md for normal product behavior changes.

LEVEL 2

Implementation plan

plan.md only for multiple slices, migration, rollout, compatibility, or material risk.

LEVEL 3

Initiative map

Several coordinated outcomes and decision tracks that cannot remain one coherent spec.

SEPARATE GATE

ADR

A real trade-off whose result is durable, hard to reverse, and surprising without context.

Behavior gate

The developer chooses unresolved product policy and accepts material behavior contracts.

Plan gate

A consequential multi-slice or migration plan is accepted before implementation.

Decision gate

The developer owns durable contested trade-offs after receiving a recommendation.

Action gate

Commit, push, PR, deploy, merge, publish, and external mutations require explicit authorization.
